# Development startup and agent login

Run against an isolated destination development deployment. Follow the [canonical development guide](../../instructions/development.md) for the selected target, frontend origin, backend settings, and intentionally guarded agent prerequisites. Convex CLI identity and the application user are separate. This recipe requires real command and backend results, not only source inspection.

## Drive

1. Before the first backend startup, install and run auth generation followed by Confect generation. Select the destination development deployment with the Convex CLI and configure its frontend/backend settings. Record the selected deployment kind and actual public endpoints without credentials.
2. Stop existing development watchers, then run `bun run dev:cloud` for the selected dev backend. Confirm fetched app variables populate `.env.local`, required remote values cannot be replaced by stale local values, connection metadata matches the selected target, and private values remain out of browser data/logs. Confirm generation finishes before backend bundling and the API becomes ready before Vite starts. Stop this run and retain its fetched app seed. Run `bun run dev:anonymous` with that explicit `.env.local` seed and an actual cached backend version where needed. Confirm only app values seed the owned local target, the API/site URLs are recomputed, the frontend uses the requested strict `PORT`, and no cloud key/URL is uploaded as app data. Confirm `dev:all` applies the same fetch/seed policy for its selected target.
3. Open the app and finish an ordinary sign-up, task creation, and reload. Confirm the app user and persisted task belong to that Better Auth session. Startup alone must not grant that ordinary user an admin role.
4. In separate verification attempts, occupy the frontend, local API, or local HTTP-site port. Confirm `dev:all` checks the ports selected by its allowed local flags and exits before generation/startup, leaving each existing process alone. Confirm unknown/selector flags, non-loopback API/site origins, a missing development selection, contradictory deployment/key selections, and a mismatched cloud API origin or nondefault HTTPS port are rejected. Do not contact production or staging deployments. Normal logged-in cloud startup with a matching selected `dev:` deployment must work without a key. With existing watchers retained, start only missing individual commands instead.
5. With agent prerequisites intentionally configured, run `bun run agent:login`. Confirm success reports `cloud-agent@localhost`, role `admin`, the frontend origin, and private temporary file paths. Inspect the verified `whoAmI` result or protected overview to confirm `system:access` is exactly `true`. Import the returned session through the supported harness mechanism and open the read-only admin panel.
6. Run `agent:login` again and confirm it reuses the designated application user while issuing a valid session. Confirm missing/wrong secrets, an unavailable app, or a disabled backend development guard fail without printing credentials. In local/anonymous verification, confirm non-loopback API/site endpoints and a supplied cloud key are denied. Hosted agent login should require the selected development target and app secret without an extra deploy key; a supplied key must match. `CONVEX_AGENT_MODE` must be rejected in both branches.
7. Stop the aggregate with Ctrl+C and confirm its recorded child processes stop, including the frontend and local backend it started. Keep unrelated processes running. Hash the anonymous seed file before activation and after stop; the original bytes must match, and its updated local metadata must be archived. Cloud mode instead retains freshly fetched app values. Repeat a failed-startup cleanup and cancellation during preparation where supported; confirm no late child launches and a later run can start after its owned ports are released. With optional agent guard fields omitted from an explicit local seed, confirm stale backend guard fields are removed before the frontend starts, while application data stays present.

## Evidence and cleanup

Record revision, deployment kind, actual origins/ports, forwarded local version, command exit codes, generation/readiness order, user/admin identity, resulting task state, and owned-process cleanup under `.verifications/<run>/`. Redact secrets, deployment credentials, cookies, tokens, and the contents of temporary login files.

A generated browser-state file is not proof that a browser used the session. Record the authenticated app continuation and protected overview result. Restore verification-only backend settings and remove the temporary credentials after use. Stop only processes owned by the run. Missing access or an unperformed command is an explicit verification gap.
